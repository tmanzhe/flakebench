# flakebench

I built flakebench to see how often an agent gets the same task right across repeated runs. It calls an OpenAI-compatible chat completions endpoint, executes Python tools, and checks the final answer.

I report numbers only from `examples/heldout.yaml`. `examples/dev.yaml` is for iteration. The seven held-out tasks cover all four checkers and several tool sequences. Mock numbers are a simulation.

From a fresh clone, with Python 3.10 or newer:

```sh
cd flakebench
python -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
pytest -q
flakebench run examples/heldout.yaml --model mock
```

For a local endpoint with an available model:

```sh
BASE_URL=http://localhost:11434/v1 flakebench run examples/heldout.yaml --model llama3.1 --seed 42
```

`API_KEY` is optional. `BASE_URL` includes the API prefix, such as `/v1`; a full `/chat/completions` URL also works. The model comes from `--model`, then the suite's `model` field, then `gpt-4o-mini`.

```text
flakebench run suite.yaml [--model NAME] [--runs N] [--seed S] [--out DIR]
```

I use 20 runs per task by default. Each invocation writes `results.jsonl` and `report.md` inside `--out`, or a new directory under `results/`. Existing results are never overwritten. An omitted seed is generated and recorded. Completed benchmarks exit 0 even with failed runs; configuration and output errors exit 2.

I use [heldout.yaml](examples/heldout.yaml) as the configuration example. Each task has an `id`, `prompt`, and `checker`, with optional `system`, `tools`, and `mock` fields. Suite defaults are `max_steps: 8` and `timeout: 30`; tasks can override both. Each run has a separate process. Its deadline includes startup, HTTP, tools, and checking. A final answer must arrive within `max_steps` model calls.

| Checker type | Fields | Check |
| --- | --- | --- |
| `exact` | `expected: 'text'`, optional `strip: true` | Case-sensitive equality; whitespace counts by default |
| `regex` | `pattern: '^text$'` | Python regex search |
| `json_schema` | `schema: {...}` | Parse JSON and validate with Draft 2020-12 |
| `python` | `function: my_checks:accepts` | Call `accepts(answer_string)` for a truth value |

Tools define `name`, JSON Schema `parameters` of type `object`, and `implementation`. Python implementations use `module:function`, take keyword arguments, and return JSON-serializable values. Modules come from the working directory or installed packages. Builtins are `builtin:add`, `multiply`, `echo`, `lookup`, `fail`, and `sleep`, each with the `builtin:` prefix. Calls execute in order and return results to the model. Python code has your account's permissions; isolation enforces deadlines, not a security sandbox.

The first failure ends a run: `wrong_answer` for rejected answers or checker exceptions, `bad_tool_json` for malformed or schema-invalid arguments, `tool_error` for raised or unknown tools and unserializable results, `timeout`, or `step_limit`. Endpoint and response-envelope failures use `model_error`.

JSONL records each outcome, answer, message history, seeds, limits, and elapsed time. The report includes pooled and per-task pass rates with Wilson 95% intervals, taxonomy counts, and flakiness: the fraction of tasks with both passes and failures.

The offline mock uses `mock.answer` and sequential `mock.tool_calls` hints. `mock.expected` and an exact checker's `expected` are answer fallbacks. With enough time, the same suite and seed reproduce outcomes; timings vary. Real endpoints may ignore seeds.

Each failure defaults to probability 0.05. I can override rates at suite or task level, with task settings winning:

```yaml
mock:
  failure_rates:
    wrong_answer: 0.10
    bad_tool_json: 0.05
    tool_error: 0.05
    timeout: 0.05
    step_limit: 0.05
```

Overrides merge with defaults and must sum to at most 1. Set all five to 0 to disable injection. Internal mock tools exercise bad arguments, exceptions, and loops; timeout injection sleeps. Injected wrong answers always fail, even with a permissive checker.
